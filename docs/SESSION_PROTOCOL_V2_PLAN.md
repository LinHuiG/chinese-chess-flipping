# 用户重连、代码简化与协议 v2 改造建议

> 2026-09-29 实施更新：v2 已在本地实现并进入集中验证，实际线协议以 [PROTOCOL.md](PROTOCOL.md) 为准。为减少重复加密，本次没有新增房间内层 AEAD：中转正文不解码，保留现有 TCP/WSS 链路保护与 UDP 会话加密。服务器 IPv6 反射未加入，但客户端全局 IPv6 候选可独立交换。下文是设计归档，末尾“仅方案”的表述属于当时阶段；最新检查见 PROJECT_STATUS.md。

日期：2026-09-29。状态：已审阅代码，尚未实施。本轮只输出方案；用户已明确要求减少套壳、允许破坏性更新、连续 60 秒无有效心跳才清理，以及本地用户名、默认房间名和对方断线提示。后续确认：断线计时继续、以房主为准；支持网络波动、App 重启和网页刷新恢复；服务器不做任何业务持久化，重启后一切作废。其他技术细节仍是建议，不记为已实现或已验证。

## 1. 当前问题与架构选择

- `server/src/hub.rs:116` 每次连接创建新用户，同 DID 先清理旧用户；`:138` 断开立即退房判负。`net.rs:25` 的连接析构触发清理，TCP/WS 当前均为 30 秒心跳期限。
- Android `GameService.java:120` 和 Web `app.js:98` 断线清空棋局，收到 SESSION 又清空一次。只改超时或保存 userId 无法恢复对局。
- `net.rs` 解析完整 JSON，`hub.rs:442` 克隆 action、重组 FORWARD，快照也再次序列化，`wire.rs:107` 按目标连接重新加密。广播已有共享 Bytes，应保留，但不是入站到出站透传。
- Android 直连/中转使用不同回复，`directRequests/directActions` 承担转换；普通请求超时还会关闭健康连接。优先简化这些重复路径。

建议保留 Rust 单服务、房主裁判、服务器管理用户与房间、Android UDP 可选直连，符合低服务端资源目标。App 重启/网页刷新通过房主本地完整存档恢复，不把棋局搬到服务器。没有证据称现状“最优”，也不必再引入通用框架；本方案仍沿用信任房主的规则。

合并纯转调和重复状态分支，展开难读长行；不增加 Manager/Factory 等套层。现有 GameConnection 有 TCP、WS 两种实现，规则引擎、资源清理和加密边界有实际用途，不按调用次数机械内联。房主自己的操作与对端操作使用同一裁判队列。

用户再次明确：以清晰、正确为前提尽可能减少总代码量，只保留确有必要的抽象。新增接口、类或模块必须解决当前真实的复用、职责/资源归属或协议差异；不为假想扩展预建框架。直接调用即可完成的流程直接写，统一直连/中转的重复逻辑，完成替换后及时删除废弃实现；同时保留必要的权限校验、消息代次、去重和有界资源处理。

整体实施范围为：精简现有代码 → 用户/连接解绑及 60 秒清理 → Android/Web 本地完整存档与恢复 → 昵称、默认房名和断线呈现 → v2 统一消息与不透明转发 → P2P 候选隔离、网络变化重协商及双栈能力评估 → 集中验证和更新交接。允许破坏旧协议；服务器无业务持久化，房主计时继续且权威不变。本轮仍为方案整理，不代表已开始代码改造。

房间版本是一个递增整数，用于拒绝旧上下文的迟到请求，不保存历史。例如 A 与 B 等待时 A 发出准备请求，B 离开、C 加入后旧请求才到，roomId 没变、等待阶段也没有 gameId，仍需房间版本阻止旧准备影响新成员。只在成员/房主、开局和结束变化时更新；每步走棋用棋面序号，单纯重连/昵称/心跳不改变房间版本。v2 可以用 serverBootId + roomId + 开局时的房间版本唯一标识本局，省去独立随机 gameId；这是协议简化建议，实施时统一替换所有上下文引用，不能删掉对旧消息的隔离。

## 2. 用户与连接解绑

| 项目 | 建议行为 |
| --- | --- |
| 用户记录 | userId、房间关系、最后有效心跳、可选连接及连接代次；socket 只负责收发 |
| 意外断开 | 立即释放连接资源，解除绑定；保留用户、房间席位和客户端棋局 |
| 离线期限 | 每 5 秒心跳，按服务器单调时钟的 lastHeartbeat + 60 秒清理；断线不能重新延长 60 秒，普通业务/坏包不续期 |
| 恢复 | 验证凭据及有效恢复握手后更新期限，绑定新连接；返回当前房间并同步。旧连接回调按代次丢弃，不删除新连接 |
| 超时清理 | 用户、房间关系、请求、UDP 登记凭据仅清理一次；一方超时按离开结算，双方均过期直接清理，避免遍历顺序决定胜方 |
| 主动退出 | 显式 LEAVE/LOGOUT 立即执行；socket close、页面刷新、进程消失不冒充主动退出 |

身份建议：服务器分配随机 UUID 和绑定身份的不可猜测恢复凭据（例如 32 字节随机 token），只在内存用户表保存凭据校验值；Android 本地按服务器保存。公开 userId 不能单独作为接管凭证。时间前缀加序号不能恢复旧身份，还要处理同秒重启与时钟回拨，复用 UUID 更简单。超过 60 秒被清理后，旧凭据作废，再连接分配新身份。

网页能存储：建议 sessionStorage 保存页面身份并跨刷新恢复；不可用时仅存内存，新页面重新分配。新标签页一般独立；复制标签页/带 opener 打开的页面可能复制初值，要检测并发使用、分配新身份，避免互踢。[浏览器存储说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)

用户已确认服务器不做任何业务持久化：取消此前持久化签名密钥及跨重启身份恢复建议，不增加数据库、用户文件或棋局文件。每次启动生成随机 serverBootId；重启后用户、token、房间、对局、直连登记全部消失。客户端收到新启动标识/会话失效结果后清除旧恢复存档，领取新身份回大厅，本地昵称和服务器设置保留。

## 3. 用户名、默认房名与断线提示

- App 设置用户名，本地保存，每次连接成功后上报；在线修改时也立即上报。身份校验一律使用 userId，昵称允许重复。建议昵称 1～24 个 Unicode 字符、去首尾空白、禁止控制字符；未设置时使用“玩家”加短 ID。
- 按用户“服务器不存”的要求，不建昵称资料库，也不在用户记录长期缓存昵称，只做校验和转发。加入房间或成员重连时，通知仍在线的成员重新发送昵称；客户端保留已收到的昵称，无资料时显示短 ID。
- 创建房间预填“用户名的房间”，仍允许编辑。生成时遵守房名 32 字符限制；改昵称不自动重命名已存在的房间。房间名称仍作为既有房间运行数据保存在内存，它不等同于服务器保存用户昵称档案。
- 服务器已观察到连接关闭时立即通知另一方：名字/头像置灰并显示“对方重连中”，保留棋面。成功重新绑定后先显示“同步中”，状态同步完成再恢复亮色和操作。
- 网络黑洞不能瞬间发现：建议超过两个心跳周期（约 10 秒）没有有效心跳先标“连接异常”，60 秒才清理；该早期提示是推测，恢复心跳即撤销，不能提前判负。状态事件带成员身份、连接代次/递增版本，忽略迟到通知。
- 自己断网时提示“你已断线，正在重连”；不能把本机失联误写成对方掉线。颜色配合文字，不只靠灰色表达。计时按下一节规则，不因 UI 置灰重置。

## 4. 客户端存档与棋局恢复（用户已确认范围）

- 支持网络波动、App 重启和网页刷新；前提是服务器仍为同一实例、用户/房间尚未过期，并有完整本地存档。60 秒后或服务器重启后不能用客户端存档复活已清理房间。
- 房主保存 GameEngine 完整状态：暗棋真实布局及翻开标记、颜色、回合、吃子记录、判重历史、操作去重记录、状态序号、计时截止点，以及 serverBootId/用户/房间/对局上下文。客人保存身份、公开快照和未确认操作，不保存暗棋身份。
- Android 使用私有目录原子替换存档，顺序写入放在后台串行队列；网页刷新用 sessionStorage 保存该标签页存档。关键状态变化时保存，不按倒计时每秒写盘。存储失败应明确提示并停止发布未保存的新状态，不能声称已具备刷新恢复能力。[AtomicFile](https://developer.android.com/reference/android/util/AtomicFile)、[sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)
- 房主处理合法动作时，先形成并成功保存新状态及操作去重结果，再确认/同步给对方；发送方先保存未确认 operationId，恢复时可重试。开局初始暗棋在 START 前存档，以开局操作号关联服务端分配的 gameId，补齐“服务端已开局但房主没收到回复”窗口；结束结果也保存到服务端确认结束。不要等 onStop/pagehide 才保存。
- **断线期间计时继续，以房主为准。** 同一次 Android 系统开机内用 elapsedRealtime 的绝对截止点跨 App 进程恢复；该时钟包括休眠时间。网页持久化房主本地绝对截止时间，刷新后计算剩余时间、重建页面单调时钟截止点；运行期间仍使用单调时钟。不把保存的剩余秒数直接当新一轮额度。[Android 时钟说明](https://developer.android.com/reference/android/os/SystemClock)
- 房主恢复时先核对服务端身份、房间和本局，再恢复存档；如果原截止点已过，先判当前行动方超时，不能先接受新动作。客人倒计时仅显示，房主进程不在时客人不自行宣布胜负。30 秒走棋超时可早于 60 秒清理；若房间已被清理，以服务端当前生命周期为准，不重放旧结果。本地改钟不作可信反作弊保证。
- 重连绑定连接不改变 roomVersion/gameId，不重新开局。当前房主/成员/对局不匹配的存档丢弃，等待房主完整快照；房主私有存档损坏不能从公开快照重建或重新随机棋子，应明确告知该局无法恢复。
- 已失去服务器控制连接的一端停止提交新动作，不能借 UDP 无限继续。恢复先同步上下文，重建直连时换通道密钥/代次，不恢复旧加密计数器。普通操作超时只结束请求或同步，不关闭仍有心跳的连接；跨通道重试用相同 operationId 去重。
- 离线期间不积压全部消息；服务器只在房间内有界保留最终结果等生命周期信息，房主提供当前公开棋面。双方同时恢复时，先等待房主完成存档加载，再同步客人并恢复正常操作。

## 5. 协议 v2 与转发

1. TCP/WS 使用同一二进制消息格式，TCP 带长度，WS 用二进制帧；路由头放必要命令、关联号、房间/对局代次、状态序号与长度。去掉 JSON 套 JSON、无关联事件随机 TID 和不必要的多套请求编号。
2. 服务端处理身份、心跳、昵称转发、房间、开局/结束和直连信令。棋局动作/快照作为不透明包体，只检查连接身份、成员权限、路由上下文和大小，再原样转发。actor 来自绑定连接，路由上下文纳入认证，不接受自报房主或任意目标。
3. 加密房间的业务包体由客户端加解密，可扩展现有 UDP 密钥分发机制供中转复用；业务编码、确认和去重统一。服务器仍可能接触分发密钥，不宣称服务器无法解密。控制链路保护不能删除；TCP 外层加密或 TLS 若覆盖整帧，仍有链路加解密成本，不承诺完全消除。
4. Bytes 切片/共享引用减少应用层包体复制，尽量使用已有缓冲区写出。WS 掩码/封帧、TLS、内核收发仍可能复制，准确目标是少复制、不解析业务包体。[Bytes 说明](https://docs.rs/bytes/latest/bytes/struct.Bytes.html)
5. 保留普通 HTTP 网页。浏览器原生 WebCrypto 加密依赖安全上下文；建议 HTTPS 网页/Android 协商端间加密，普通 HTTP 网页参与的房间沿用既有明文边界并透传，不默默禁用 HTTP 或引入自研密码实现。[WebCrypto 限制](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/encrypt)
6. 包体先保留小型 JSON，32 格棋盘继续全量快照，不急于引入压缩、复杂增量和二进制棋盘。UDP 超过现有 1200 字节预算走可靠链路。

v2 不兼容旧客户端业务，但要明确提示升级。精确字节布局、认证覆盖和加密协商应在实施时写入 PROTOCOL.md，不能把本节当成已完成的线协议规格。

## 6. 其他简化与执行顺序

- 服务端继续使用一个 Tokio 运行时及可配置工作线程。业务只需直接的数据结构和处理函数：用户表（身份/token 校验、心跳、房间、当前连接代次）、房间表（名称、成员、房主、状态、版本/对局及必要结算信息）、连接收发对象；UDP 协商记录按有效期清理。昵称只转发，不建用户资料存储。
- 连接先完成握手，再处理首次注册或恢复；恢复在同一临界区校验未过期凭据、切换连接代次，随后关闭旧 socket。读取、写入和关闭回调都校验所属代次，防止旧连接继续发操作或误删新绑定；各连接写出保持顺序，有界队列满时关闭慢连接并进入正常重连宽限。
- App 网络层统一接收/发送业务消息，TCP 与 WS 只做承载适配。服务器链路始终维持心跳及控制命令；Android 双方确认直连后棋局包走 UDP，其余情形走服务器，失败沿用同一 operationId 回退。Web 走 WS/WSS。重连先恢复身份/房间、上报昵称、核对本地存档、同步棋面，最后重新尝试直连。
- 先移出 Hub 全局锁中的复制、序列化和实际发送；目标连接与代次在锁内核验。不先引入分片锁/Actor 框架，后续依据实际锁等待决定。
- 保留有界队列、慢连接处理、握手时限，补消息字节预算及恢复中用户上限，避免 60 秒宽限放大内存。在线期限统一调度，过期 UDP 登记也主动释放。
- v2 移除与认证保护重复的 CRC、冗余长度及转发映射；保留边界校验、防重放和操作去重。端点负责业务确认，服务器控制命令仍有明确结果。
- 增加简短的直连阶段/失败原因码，避免所有问题只显示“中转”；不记录密钥和完整身份/地址。候选地址失败不应无条件结束全部候选探测，结合现有排查记录实施。
- v2 完成后，先保留有价值的 Android 规则/互通夹具，再删除旧 Java 服务和仅为 v1 存在的兼容路径。
- 顺序：用户/连接解绑与 60 秒清理 → 两端完整本地存档、恢复计时、昵称及断线 UI → 统一业务消息及 v2 透传 → 清理旧代码。开发仅必要编译；完成后集中检查恢复接管、App 重启/网页刷新、落盘与回包窗口、迟到回调、60 秒清理、服务器重启失效、跨通道去重、混合客户端及资源变化。

## 7. 跨 Wi-Fi/5G 直连失败复核与补充建议

证据来源为用户提供的其他线程交接及 PROJECT_STATUS.md，本线程复核代码，没有重新连接服务器、抓包或操作模拟器。既有对照表明：同一组设备同网 Wi-Fi 可直连，手机 5G 时模拟器侧游戏 UDP 入站为零，服务端登记和地址交换已发生。支持“此次跨网 IPv4 双向通路未建立”，不能据此定位运营商 NAT、家庭路由器、模拟器转发或具体过滤点，也不能归因于已修复的到包后来源检查。

代码确认：

- `UdpPeer.java:55` 只取服务器 IPv4，`:57` 绑定 IPv4 socket，`:62` 只收集 IPv4，`:67` 候选解析也只接收 IPv4 文本；IPv6 需调整完整路径，不只是放开一处地址判断。
- `UdpPeer.java:82` 任一 sendPacket 异常调用 fail，关闭整条直连；`:107` 初始尝试 10 秒。要区分单候选发送失败与整个 socket/加密会话失效；前者跳过该候选，后者终止本轮。
- `GameService.java:371` 每个对局上下文只发起一次协商，没有默认网络变化回调；失败后的原地重试不等于重新收集有效路径。
- `main.rs:36` 服务端 UDP 只监听 IPv4；`hub.rs:72` 每人只存一个反射地址，`:649` 只接受首次登记。`peer_endpoints` 还要求双方反射登记齐全后才交换候选。网络切换和双栈支持必须同时改服务端协商，不仅改 App 定时器。

建议顺序：

1. 加阶段、失败原因及收发数量诊断，区分未收到候选、无入站、认证失败、单向可达和候选发送错误。客户端使用有界本地记录，服务器正常输出脱敏运行日志，不新增业务持久化；不保存 IP、密钥、token 或完整用户身份。普通界面仍显示中转，诊断详情按需查看。
2. 候选分别探测，单地址不可达不影响其余地址；成功仍需双向认证。保持 0.5.1 已修复的多来源接收，不重新锁死入站来源。
3. 监听 Android 默认网络及地址变化，等待地址/路由就绪并去抖；先恢复可靠控制链路，再发起新协商、创建新 socket、重新登记并分发候选。新协商 ID/token/密钥替换旧值，两端切换后才激活；无网络变化时最多有限重试，带退避且限制总探测预算，已有中转继续服务。[Android 网络变化说明](https://developer.android.com/develop/connectivity/network-ops/reading-network-state)
4. 收集并核实双方实际可用的全局 IPv6，再增加 IPv4/IPv6 候选及双向探测，不等待 IPv4 登记成功才发送已取得的有效候选。IPv6 候选可以经 IPv4 控制链路交换；要观察 IPv6 反射地址，则服务端 UDP 也需双栈监听及按地址族保存映射，部署网络必须实际可达。不能把 link-local 地址当跨网公网地址，也不能把“手机有 IPv6”当成“两端 IPv6 能互通”。参考 [ICE 候选收集](https://www.rfc-editor.org/rfc/rfc8445.html#section-5.1.1)，不为当前游戏直接引入整套 WebRTC。
5. 仍失败时再安排双方真机 IPv6/IPv4 对照、手机侧入站证据或受控多目标映射检查。后者用于识别映射行为，不是保证打洞成功的修法。不先做端口扫描或端口预测；不因为一次网络组合失败重写棋局协议。

目标相关 NAT 映射可能使服务器看到的端口不适用于对端，IPv6 也仍可能受防火墙影响；这些是候选机制，不是本次已确认根因。[RFC 5128](https://www.rfc-editor.org/rfc/rfc5128.html#section-5.2)

继续保留现有 TCP/WS 中转兜底。TURN 仍然是中转，不能用它宣称实现了直连；当前低频棋局已有可用中转，不默认新增 TURN 服务。以上建议未验证能修复该组 Wi-Fi/5G 网络。

## 8. 服务端文件结构

| 现有文件 | 当前职责 | v2 调整方向 |
| --- | --- | --- |
| main.rs | 配置、Tokio 运行时、TCP/HTTP/UDP 监听、过期任务启动 | 保持入口简单，补所需双栈及统一到期调度 |
| net.rs | TCP/WS 握手与收发、连接存活判断、网页静态资源 | 只负责连接生命周期和收发，关闭时解绑用户，不直接退房 |
| wire.rs | TCP 帧边界、长度、CRC、密钥派生与加解密 | 共同 v2 帧、路由头及相应保护，减少重复编码和复制 |
| hub.rs | 用户/房间表、权限与命令、转发、P2P 协商/登记 | 用户与连接解绑，60 秒清理，包体透传及可重新协商 |
| json.rs | JSON 解析、重复字段/格式校验 | 只为服务端要理解的控制内容服务，不解析棋局透传包体 |

服务端仅保留 Rust；旧 Java 迁移参考和测试已清理，网页位于 `server/src/main/resources/web`。建议沿用这些职责边界，用结构体和普通函数直接调用；只有 P2P 双栈/协商逻辑显著增长时再考虑独立 p2p.rs，不预建 Service/Repository/Factory 层。
