# 房间广播与成员 UDP 互连方案

2026-10-13，设计依据；0.8.0 已实现指定广播、通用授权及跨端语音，精确字段见 [接入手册](CYBER_ROOM_INTEGRATION_MANUAL.md)，验证结果见 [执行记录](../PROJECT_STATUS.md)。使用 UDP 单播，获准成员互连；已选择 P2P 发送的目标不再重复交给广播，房主不代转其他人语音。

已接入探测丢包、RTT 变化及本地发送积压选路，异常时减少直连目标；使用有界队列与过期丢弃，处理换网/前后台，语音失败不阻止观看和弹幕。没有上行带宽估计器；探测指标不能写成实测媒体丢包率。回声设计见 [观影方案](WATCH_ROOM_PLAN.md#回声消除与音频能力降级)。

## 当前已有能力

`room.js` 的 `setupPeers()` 遍历全部支持 UDP 的房间成员，以双方 clientId 的顺序决定协商发起者，没有仅连接房主的限制。`peer.offer/answer` 经现有 SEND 转发；UDP_DISCOVER 返回观察到的地址。`UdpPeer` 用一个 DatagramSocket 管理多个 Peer，当前最多 16 个对端，每个对端独立密钥和路径状态。

因此，成员互连的拓扑主要属于客户端。服务端仍提供发现、信令转发和失败后的中转，不是完全不参与。新广播操作、广播成员授权和通用资源限额则需要 Rust 调整。现有机制能尝试成员互连，不代表六人语音或公网任意组合已经验证。

## 每个说话者独立发送

每个人只采集并编码自己的声音。对当前获准接收成员，发送者划分两组：有可用原生 UDP 路径的成员，以及需要服务端转发的成员。前一组逐目标单播，后一组把相同正文加目标名单上传一次，由服务端分别发送。两组都排除自己。

例如六人 H、A、B、C、D、E 中，A 能直连 B/C，不能直连 H/D/E：A 分别向 B/C 发 UDP，再调用一次广播指定 H/D/E。H 只接收和播放，不帮 A 再转发。其他说话者各自执行相同流程，不要求整间房统一选择直连或中转。

编码后的音频正文可以复用；各 UDP 对端及 TCP 连接的外壳仍用各自密钥、nonce 加密。不能把一个对端的密文原封不动发给另一个对端。接收者对每个说话者独立做排序、抖动缓冲和解码，再本地混音，不需要房主或服务器混音。

## 通用广播的最小语义

已采用 `BROADCAST(201)`，沿用 17 字节外壳、扩展控制区原样透传及二进制正文，不加入服务端语音、游戏或媒体字段。下表为设计依据，实际授权、to、discard、maxAgeMs 和入队计数按接入手册执行。

| 项目 | 建议约定 |
| --- | --- |
| 房间 | 必须指定 roomId，并校验发送者当前获准身份 |
| 接收目标 | 未指定时为本房当前获准成员中的其他在线成员；指定时仅投递列出的合法成员 |
| 空目标集合 | SDK 不发送；不能把空集合误编码为省略字段而变成全房广播 |
| 名单 | 有界、去重，只能在本房授权范围内选择，不能借此向其他房间发送 |
| 来源 | 服务端追加真实连接来源 from，不允许调用者冒充他人 |
| 正文 | 原始字节，不做 JSON 解码，不识别音频或弹幕 |
| 回执 | 可选汇总本次入队结果；不等于每人收到或播放成功，不给每个音频帧配业务确认 |
| 离线与失败目标 | 不补存历史；逐目标处理，部分失败不撤销已发送内容，也不阻止其他目标 |

具体目标字段及编码在实施时与 SDK、保留字段校验一起定稿，避免同时设计接收名单和排除名单两套重复机制。新旧服务端需做能力判断或明确版本门槛，不能向不支持的旧服务端盲发新功能号。

广播必须与 R1 的成员核对一起落实。当前 routes 在房主批准之前就会登记，不能直接遍历 routes 向所有关联广播，否则未获准的申请者也可能收到内容。房主决定批准与移出，服务端仅保存/检查执行广播所需的通用授权状态，不解析裁决正文，不决定谁能看什么电影。即使收到广播，客户端仍按来源检查房主专属操作等业务权限。

## 路径切换与失败处理

P2P 目标按近期经过验证的路径状态选择；本地 send 返回 true 只代表入队，不能称为已送达。当前 `sendTo(auto)` 失败会逐目标退回 SEND，因此语音广播调度需要先收集未走直连的目标，再统一广播，避免无意中恢复为多次上传。

同一音频帧在两条路径上使用相同的说话者身份、流代次和帧序号，接收端以此短期去重，防止路径切换时播放两次。换麦、重启或重建流更换流代次；仅合法重排范围内的包进入缓冲，旧音频过期丢弃，不套用游戏动作的长时间重试。需要可靠到达的控制操作另用确认及补同步。

只将故障对端切到中转，恢复探测退避并避免来回抖动；R3/R4 的回执及双向路径验证仍需修复。UDP 打洞取决于两端 NAT 行为，不能由“双方都连接过服务端”推断一定能互通，应保留中转。[RFC 5128 的 NAT 穿透与中转说明](https://www.rfc-editor.org/rfc/rfc5128.html)

移出/退出时，所有客户端根据房主更新撤销该对端的业务授权并清理连接；不能只依靠被移出者主动断开。普通网页缺少现有原生 UDP 适配时走 WS 广播中转，Windows 原生适配尚未开发。房主仍负责成员裁决和播放同步；全互连不会改变房主不可用时暂停等待及退出解散规则。

## 六人负载估算

以下假设六人同时说话，每人音频编码为 32 kbit/s，每 20 ms 一帧，即 50 帧/秒；不是已选编码配置或性能实测。表内仅统计音频正文，不含协议头、加密、IP/UDP、保活和重传开销。

| 模式 | 每人上传 | 每人接收 | 房主额外转发 |
| --- | --- | --- | --- |
| 全部 UDP 互连 | 自己的声音发五份，160 kbit/s、250 包/秒 | 其他五人的声音，160 kbit/s、250 包/秒 | 无 |
| 全部走服务端广播 | 自己的声音上传一份，32 kbit/s、50 请求/秒 | 其他五人的声音，160 kbit/s、250 包/秒 | 无 |
| 混合 | k 名直连者各一份；若还有中转目标，再上传一份给服务端 | 各对端按可用路径到达，总共仍最多五路声音 | 无 |

原房主星形方案在全员讲话时，房主需要发送自己五份及其他五人的各四份，共 25 路正文。全互连后房主只发自己五份，语音发送份数降为原来的五分之一；其他成员的纯直连上传则从一份增加到五份。房主仍要编码自己、解码混音最多五路、播放电影和管理房间，并非没有负载。

六人的最大对等关系为 6 × 5 / 2 = 15 条，每设备五个 Peer；现有一个 UDP socket 可以复用这些 Peer，不是每人必须开 15 个 socket。若以后评估十人，则总计 45 条关系、每人九个 Peer，但不因此更改当前观影六人的范围。连接维护总量随人数平方增长，不能据小房间估算直接宣称支持大房间。

全中转时，服务端总入站从旧星形路径的约 1,500 个音频请求/秒降到 300 个广播请求/秒，每用户约 50，消除旧方案房主集中达到 1,250 请求/秒的问题；服务端仍需投递 6 × 5 × 50 = 1,500 份/秒，每个接收端约 250 份/秒。因此广播解决重复上传和额外转发路径，不会消除出口、加密和慢接收端负担。

现有输出队列只有 32 项，满时关闭连接，这个边界仍需定向验证。广播按实际目标数量与字节数核算扇出资源，不能只统计“一个请求”就允许无限放大。一个慢端的入队失败不能中断其他目标；通用服务端不识别音频，不能暗中按媒体类型丢包。实时丢弃优先由客户端在发送前及播放缓冲中处理，队列限额/关闭策略保持通用，并给控制流保留合理资源。

原生音频应避免逐包穿过 JS/Base64/UI 回调。现有 UDP 接收会遍历 Peer 尝试识别来源，高包率时的重复解析、分配和耗电应测量后再局部优化，不先引入复杂连接框架。六人全双工的解码、混音、回声和设备切换仍是实际工程量。

## 补充实现边界

以下方向已由用户确认；具体算法、阈值和组件仍为实施选择，不表示新增功能已经完成或设备效果已经验证。

1. **可达不等于适合语音。** 当前 UdpPeer 的 ready 主要依据最近四秒是否收到 pong；持续收到探测回复仍可能伴随语音丢包、抖动或发送排队。选路应结合实际接收统计和本地发送队列，允许质量差的直连目标退回中转。全互连还会把上传份数分散到每个说话者；低上行设备可减少直连目标，把其余目标合入一次广播。设置切换观察窗口，避免频繁反复，不先增加复杂带宽预测模块。

2. **TCP 中转有时延边界。** TCP 提供可靠、有序字节流，丢失数据的恢复可能阻塞后续数据交付；广播减少重复上传，但不改变这一性质。音频和控制共用连接时，仅给应用队列设优先级不能越过已经写入 TCP 的旧数据。客户端应限制发送前的积压、丢弃过期音频，接收端只播放仍有时效的帧；后续暂停、踢人等控制仍需在弱网场景验收。首版沿用现有中转，若验收不满足实时性再评估传输调整，不把服务端 UDP 中转提前列为本轮前置要求。[TCP 规范](https://www.rfc-editor.org/rfc/rfc9293.html)

3. **换网和恢复要主动重建有效路径。** 本轮源码检索未发现 Android 网络变化回调；当前地址发现主要发生在建房、入房和连接恢复时。Wi-Fi 与移动网络切换后，应使旧路径失效、重新发现地址及协商，恢复期间利用可用中转，旧协商结果不能覆盖新状态。MainActivity 当前 onResume 仅处理安装恢复，onStop 直接上报 background；观影实现需补前台恢复同步，并区分真正退后台与界面重建。涉及密钥重建时不能在旧密钥下重置加密序号。[Android 网络变化说明](https://developer.android.com/develop/connectivity/network-ops/reading-network-state)

4. **电影外放与持续开麦必须一起验证。** 麦克风可能把电影和其他人的声音再次发回房间。音频实现要处理回声消除，并确认实际播放器输出是否被正确纳入处理；不能仅因设备存在 AEC 就宣称外放可用。Android 的 AEC 本身也需检查可用性。来电、音频焦点变化和耳机切换要保持采集与界面状态一致，沿用默认闭麦及后台闭麦规则；恢复观看不应自行重新开麦。[Android AEC](https://developer.android.com/reference/android/media/audiofx/AcousticEchoCanceler)、[音频焦点](https://developer.android.com/media/optimize/audio-focus)

5. **跨端音频与传输能力分别协商。** Android、Windows、网页即使能收到同一字节流，也不代表都能采集或解码该格式。实施时确定共同的编码、采样率、声道、帧时长及版本，独立报告发送/接收音频能力；无法开麦不应妨碍观影和弹幕。音频帧的序号、流代次与采样时间由客户端定义，不能直接比较不同设备的系统时间来安排播放。尽量让单帧连同外壳处于 UDP 包大小限制内，避免为了语音引入大帧分片依赖。

## 积压与过期丢弃的具体边界

发送端按时间和容量共同限制待发音频，满时淘汰可丢弃的旧帧；原生 UDP 发送队列、TCP/WS 写入前队列和接收播放缓冲都要覆盖。接收端按说话者的流代次、序号及已建立的采样时间映射决定播放期限，不拿不同设备的墙上时间直接比较。断线与恢复不补发历史语音，控制命令不套用音频过期规则。

服务端也要能在写出前清理过期中转数据，但不能因此解析音频正文。建议在通用投递元数据中表达“允许过期丢弃”和有上限的最大排队时长；字段名随广播协议一起定稿。Rust 只按本地单调时钟计算驻留时间，同一消息向不同目标投递时不反复刷新期限；未声明允许丢弃的消息保持现有投递语义。此机制同样可供其他实时房间数据使用，不增加语音专用功能号。

这个排队期限只约束服务器收到后、写出前的驻留，不能证明端到端音频年龄。已交给 TCP 的旧字节无法撤回，接收端仍需拒绝过期播放。完整帧尚未开始写入时才可淘汰；帧写到一半不能截掉后续字节再写下一帧，否则破坏统一协议帧边界。持续慢写应在有界等待后按连接故障处理并恢复，不能无限积压。某一目标慢不能阻塞广播的其他目标。

质量反馈使用低频、有界的统计报告，不逐音频帧确认；A 到 B、B 到 A 分别评估。静音、主动关闭麦克风与编码器主动省略的静音不能算作网络丢包，也不能以“没声音”代替连接失效判断。切换使用观察窗口和恢复退避，保留同帧跨路径去重；上行不足时合并中转目标，先减少重复上传，再按实际编码能力降低码率。

## 实施与验证边界

建议顺序为成员授权与 R1/R3/R4 修复、通用广播、复用成员互连与按目标选路、音频适配，再做六人全直连/全中转/混合路径检查。音频接入前先做短小的回声与跨端编解码可行性检查，避免播放器定型后才发现无法取得消回声参考。验收包括未获准者不能收发广播、指定目标不越界、空名单不扩散、单对端失败切换、重复帧不重复播放、慢端不拖全房、退出撤销与房主负载测量。另覆盖音频过期淘汰而控制不被误丢、TCP 帧完整性、换网重建及静音不触发错误切换；属于后续定向验收，不在归档阶段运行全量测试。

早期方案阶段仅核对代码与计算负载；后续已实现 103/201 与三端语音，但没有公网性能结论。不采用 IP 组播、WebRTC/TURN 或服务端 UDP 业务中转，视频继续由各端直接取自 Emby。实际初版 CRV1 为每帧 180 字节、每秒 50 帧，即每路 72 kbit/s（未含外层）；六人全直连每人五份约 360 kbit/s，全中转每人上传一份约 72 kbit/s，服务器总扇出约 2.16 Mbit/s。本文前面的 32 kbit/s 表格保留为旧估算，不代替当前码率或实测带宽。
