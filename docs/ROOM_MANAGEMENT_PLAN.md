## 2. 用户已确认的业务规则

### 2.1 用户、心跳和连接关闭

1. 每个 App 维护一个连接，每个 App 是一个用户，没有账号、注册和登录逻辑。
2. 客户端每隔 5 秒发送心跳。服务端连续 30 秒未收到有效心跳，就 `close` 连接。服务端依据接收情况判断，不依据客户端是否报告发送成功。
3. 无论服务端还是客户端主动关闭，或连接因异常断开，服务端都必须清理该连接相关数据，并执行用户退出动作。用户在房间中时，同时退出房间。
4. 退出、断线、心跳超时使用同一套业务清理逻辑；重复触发只处理一次。过期的房主请求、旧对局消息应拒绝。
5. 离线用户数据全部清理，不保存战绩，不保留断线恢复的用户或棋局。双方都断开后清理房间；服务端重启后用户和房间全部清空。
6. 切后台、锁屏本身不算退出：能保持连接就继续留在房间；连接断开才执行退出和相应判负。

### 2.2 自动重连与同一 App 的旧连接

1. App 在前台时，断线后每隔 3 秒重连一次。3 秒是两次尝试之间的等待时间，不包含 TCP 连接和加密握手的耗时。
2. 重连成功后进入房间列表查询页面，不恢复原房间或棋局。
3. 同一 App 新连接握手成功时，立即替换旧连接，不等待旧连接的 30 秒超时。
4. 使用现有本地随机安装标识 DID 识别同一个 App；新连接握手通过后，先关闭并清理旧连接，执行旧用户退出和必要的判负，再让新会话进入大厅。
5. DID 仅用于在线连接去重，不构成账号认证，不用于恢复旧房间。旧连接的迟到回调不能清除新连接的数据。

### 2.3 房间、列表和成员

1. 用户可以创建并命名房间，创建者自动成为房主。
2. 房间名去掉首尾空白后限制为 1～32 个字符，允许重名，以房间 ID 区分。列表条目显示为 `#ID 房间名`。
3. 一个用户同时只能在一个房间中。每个房间包括房主在内最多两人。
4. 不在房间的用户可以查询当前所有房间，列表支持手动刷新。只能加入等待状态且未满员的房间，游戏中的房间不可加入。
5. 房主退出房间时，房主资格按成员加入顺序自动转移。由于最多两人，通常由唯一剩余成员接任。
6. 全部成员退出后，房间自动解散。
7. 房主可以主动解散房间；游戏中解散时先按房主认输处理，再解散。

### 2.4 准备、开始和结束

1. 进入房间后显示等待页面，初始未准备，成员可以点击准备。
2. 必须满两人且包括房主在内的所有人都准备，才自动开始游戏。
3. 等待阶段成员发生变化时，全部重置为未准备，防止新人加入后意外开局。
4. 游戏中有人退出，包括连接关闭、超时或被新连接替换导致退出，立即结束本局，退出者判负。
5. 正常游戏结束后，双方回到房间等待页面，默认全部未准备。
6. 因一方退出而结束时，剩余用户留在房间，回到未准备的等待状态；原房主退出则同时转移房主。最后一人退出则删除房间。
7. 房主在游戏中主动解散时，先完成房主认输的结束处理，再删除房间；在线成员回到房间列表页面。

### 2.5 服务端与房主的职责

用户已接受：仅存名称和房主不足以保证成员限制和断线清理，服务端需要保存最小成员信息和房间状态。

| 位置 | 职责与数据 |
| --- | --- |
| 服务端内存 | 在线会话、DID 到当前连接的映射、用户所属房间；房间 ID、名称、房主、有序成员、等待/游戏状态，以及拒绝过期操作所需的房间版本和本局 ID |
| 房主客户端 | 准备状态、完整房间业务状态；待实现的棋盘、回合、走棋规则、历史棋面判重、每步计时及正常胜负判断，具体规则见 [棋局方案](GAME_RULES.md) |
| 其他成员客户端 | 保存同步结果供页面展示，通过服务端向房主提交操作 |

- 服务端直接处理创建、加入、退出、房主转移、解散、断线清理和退出导致的强制结束；这些操作不能依赖即将退出或已经离线的房主处理。
- 准备和棋局等详细业务请求经服务端转发给房主，房主处理后再经服务端同步给房间成员，不建立客户端之间的直连。
- 开始游戏由房主在两人均准备后请求，服务端检查当前房主、成员数和房间状态，再提交房间状态变化并通知双方。服务端不因此接管全部准备状态和棋局规则。
- 房主网络仍在线但业务未响应时，请求要有超时提示；成员始终能直接向服务端退出，不能被房主卡住。
- 用户接受房主拥有棋局裁判权的信任模型；本方案不保证修改过的房主客户端不能作弊。

## 3. 房间状态流转

仅用“等待”和“游戏中”表达对外房间状态，解散意味着房间记录已删除。

| 当前状态 | 事件 | 处理结果 |
| --- | --- | --- |
| 无房间 | 创建 | 创建者为房主，1 人，等待，未准备 |
| 等待、1 人 | 新成员加入 | 2 人，全部未准备 |
| 等待、2 人 | 两人均准备，房主请求开始被服务端接受 | 游戏中，分配本局 ID，统一通知开始 |
| 等待 | 任一成员退出 | 删除该成员，剩余成员未准备，必要时转移房主；无人则删除房间 |
| 游戏中 | 房主报告正常结束 | 等待，双方未准备，清理本局临时数据 |
| 游戏中 | 一人退出或断线 | 退出者判负，剩余成员等待且未准备，必要时转移房主 |
| 等待 | 房主解散 | 删除房间，在线成员回大厅 |
| 游戏中 | 房主解散 | 房主认输后删除房间，在线成员回大厅 |
| 任意存在的房间 | 最后一人退出 | 删除房间 |

## 4. 实现建议与必须保持的不变量

本节是配套实现建议，不代表已经选定具体类名、线程模型、错误码或报文字段。未被用户单独指定的细节可以在后续实现中按本方案目标选择，不必把日常实现选择反复作为业务确认问题。

### 4.1 心跳和前后台重连

- 握手沿用独立的绝对超时，业务心跳超时从握手完成开始计时。普通业务消息和无效报文不更新“最后有效心跳”时间。
- 建议客户端连续 30 秒未收到有效 PONG 时主动关闭，触发相同的清理和重连流程，避免只有写入成功但连接不可用的情况。这是客户端侧配套建议，服务端 30 秒心跳规则已确认。
- 前台检测到断线后等待 3 秒重连；每次尝试失败或超时完全结束后，再等 3 秒。任意时刻最多一个连接尝试，不叠加定时器。
- 后台继续维护已建立连接、心跳和房主业务处理，但不发起新的重连；已在进行的尝试必须妥善完成或取消，不能产生第二条连接。
- 返回前台时，若已断线，建议立即尝试一次，失败后再间隔 3 秒重试；若原连接仍可用，继续留在原页面和房间，不因前后台切换退出。
- 成功以完整加密握手及服务端会话登记完成为准，成功后清空客户端旧房间/棋局，进入大厅并主动查询一次列表。后续列表提供手动刷新，不要求定期轮询。
- 退出房间仅解除房间关系，保留 TCP 连接。退出 App 关闭连接并取消重连；普通连接关闭且 App 仍在前台时，按用户要求重连。
- 将连接管理、心跳和房主状态处理从 Activity 生命周期独立出来，不能继续在 `onStop()` 中无条件断开，也不能在切换页面时新建额外连接。具体后台维持方式待实现，不能将编译通过写成已经验证锁屏和厂商后台行为。
- 客户端主动关闭但网络已不可达时，服务端不一定立即收到关闭信号；服务端一旦观察到关闭就立即清理，未观察到时由 30 秒心跳超时或同 DID 新连接替换完成清理。

### 4.2 统一清理与会话替换

- 连接关闭入口与主动离房共用退出业务；主动离房不删除仍在线的会话。关闭连接则另外清理在线索引、DID 映射、该连接待处理请求及定时任务等全部关联资源。
- 同 DID 新连接必须在握手验证成功后才能替换旧连接；未通过握手的连接不能踢掉已在线用户。
- 替换时将旧会话作废并完整执行一次退出，再登记新会话。服务端业务处理需要保证顺序，旧连接后续请求不能继续操作原房间。
- 清理在线索引时比较具体会话/连接是否仍是当前值，不能只按 DID 无条件删除。客户端回调也需区分连接代次，避免旧回调覆盖新连接界面或再启动一轮重连。
- 双方同时断开时，按服务端串行处理顺序结束本局并最终清空房间，不保留需要恢复或持久化的战绩。

### 4.3 并发、权限和状态同步

- 创建、加入、退出、开始、结束及解散需要有明确处理顺序。并发加入最后一个空位时，只允许一个请求成功。
- 列表是查询时的快照；即使页面显示可加入，服务端也必须在加入时重验人数、状态和用户所属房间。
- 成员身份来自当前连接，不能信任请求体自报的用户或房主身份。房主权限由服务端当前记录决定。
- 用房间版本/成员变更代次、本局 ID、请求关联信息区分迟到操作；成员变更或换房主时，废弃已经失效的转发请求。具体字段在开发业务协议时确定。
- 等待页建议支持取消准备；成员变化和游戏结束后，房主与其他客户端都收到一致的未准备状态。旧准备请求不得在新成员加入后重新生效。
- 房主自己的准备或棋局操作也走统一同步流程。双方以服务端已经接受的开局/结束通知切换页面，不能仅因本地点击准备就认为开局成功。
- 房主迁移只需要重建剩余一人的等待状态；本方案不要求迁移正在进行的棋局，因为游戏中退出已经结束本局。
- 转发请求设置有限超时并向发起者反馈；具体超时值留待实现。超时不是已经完成操作的证明，迟到响应要校验有效性，必要时重新同步状态，不能造成重复开局或重复结束。
- 超时及房主处理不响应时，心跳和直接离房仍应可处理，不能被阻塞在房主业务队列中。

### 4.4 页面与消息协议

- 大厅条目文字保持 `#ID 房间名`，加入按钮/交互体现当前不可加入状态；不强行增加用户未要求的房主姓名等列表字段。
- 名称校验前后端一致；建议按 Unicode 码点计数以落实 1～32 个字符，避免将一个表情的代理对误算成两个字符。房间 ID 的具体格式留待实现，同一服务端实例中的已删除 ID 不应立即复用导致旧请求误命中新房间。
- 房间列表应覆盖全部房间；必要时分页或分批传输，适应现有 64 KiB 业务包体限制。
- 在已有加密协议上增加会话信息、大厅查询、房间请求、请求结果、服务端事件及房主转发/状态同步，不把主动推送误当作未知请求响应而断开连接。
- 请求响应与主动事件分别处理；转发还需关联原发起者和房主返回结果。具体类型值和字段开发时同步写入 `PROTOCOL.md`，两端共有协议源码仍按仓库约定保持一致。
- 所有发往同一连接的加密输出仍需遵守该连接严格递增的 Nonce 和发送顺序，新增业务并发不能破坏既有通信约束。
