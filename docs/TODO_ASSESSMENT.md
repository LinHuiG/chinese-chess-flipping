# 新增待办的实施评估

> 后续状态（2026-10-13）：本文保留 `d2c70cc` 上的实施前评估。用户随后授权执行，0.8.0 已完成观影、广播、Android/Windows 及 R1–R5 的修复/规避；精确完成范围和未验证项见 [执行记录](../PROJECT_STATUS.md)，不能把下文旧行号或“尚未实现”作为现状。

2026-10-13，基于远端 main 提交 `d2c70cc`。已将本工作区从 `3793eff` 快进到该提交并恢复原暂存文档。本次评估以 [最新观影与 Windows 方案](WATCH_ROOM_PLAN.md) 和 [客户端与传输待办](CLIENT_TRANSPORT_REVIEW.md) 为基线，仅分析与记录，不开始业务实现。

总体可行，但范围已经包含通信修复、生命周期、密码、六人观影、多人语音及一个 Windows 客户端，应分阶段交付。优先处理会造成状态错误的 R1–R3，再接入新模块；Emby 授权、语音包率和跨端音频能力应尽早验证，以免完整 UI 做完才发现基础路径不可用。

最新仓库方案是六人含房主、各自直接取 Emby、房间实时弹幕和自有协议语音。本聊天此前的十人、房主分发视频、随电影进度显示弹幕方案保留为历史草案，不作为本次实施评估依据。

## 正确性待办

| 待办 | 本次源码核对 | 优先级与处理建议 | 相对复杂度 |
| --- | --- | --- | --- |
| R2 主动断开后重连 | transport.js 145–154：finish 在重试等待状态提前返回，disconnect 未直接清理 retry；重试调用 connect 又会启用连接 | 最先修，影响退出、切服务器和新生命周期；无条件撤销旧重试并校验代次 | 小 |
| R3 中转重试仍走失效 UDP 回执 | room.js 154–168：重试指定 relay，回执未指定路径；publish 也默认 auto | 与 R2 同批优先。最小可选方案是关键操作回执统一可靠中转并暂保留状态修复；不能只改请求方向 | 小至中 |
| R1 恢复后幽灵成员 | room.js 33–35 只检查房间存在；hub.rs 358 在裁决前建立 routes，415 的离开通知无离线补送 | 新房间、密码恢复之前完成；先明确房主授权记录、离开撤销和快照版本契约 | 中至大 |
| R4 单向候选覆盖出站地址 | UdpPeer.java 123 在区分探测和业务前更新 remote；ready 由旧 pongAt 决定 | P2P 语音前完成。匹配本端发出的探测与来源地址，验证双向可达后才切换出站路径 | 中 |
| R5 分片与防重放窗口 | UdpPeer 允许最多 80 片，UdpSession 的窗口为 64；文档所述极端乱序原因成立 | 首先给较大可靠消息使用中转或明确直连大小边界；电影已改为 Emby 直取，无需为电影实现完整可靠 UDP | 小范围规避为小，完整可靠传输为大 |

R1 不能通过一个“返回 routes”接口直接解决。routes 同时可能包含未获准请求；只对客户端旧名单与 routes 求交也不能完整区分同一 clientId 的退出后重新申请。建议由 Rust 保存最小、由房主显式确认的通用授权状态或等价的关联代次，房主继续裁决密码和准入；不要求 Rust 解析电影或 JOIN 裁决正文。具体契约至少覆盖：批准失败、拒绝/退出清理、短时掉线、过期、同身份重新申请以及恢复快照与并发事件的顺序。现有七功能文档须随最终接口同步更新。

R3 若按来路选择回执，需要由传输层附加可信路径元数据；不能相信对端自报的路径标记。直接把关键回执放中转是改动更小的初始选择，之后有测量需求再优化。保留 messageId 去重；执行成功与执行者获知成功是两件事。

R5 仅把最大分片数减到 64 仍不能保证可靠：多消息和新增语音交错时，其他包也会推进同一防重放窗口。保留认证和防重放，按业务要求决定走中转、接受状态丢失或实现有界重传，不能把窗口扩容当作可靠性保证。

上述为独立源码复核。R1–R3 的既有离线复现及 R5 的 Java 乱序样例来自原待办记录，本轮未重复执行；R4 尚无真实 NAT 复现。

## 语音新增的容量缺口

后续讨论已调整架构：采用成员 UDP 单播互连，以及可指定接收目标的服务端通用广播，房主不再代转语音。下面 1,250 包/秒分析保留为旧星形方案的依据；新方案及仍存在的出站/队列约束见 [广播与互连方案](ROOM_BROADCAST_PLAN.md)。合包不再是规避旧房主包率瓶颈的唯一前置方案。

**六人星形语音若逐帧、逐目标发送，在全中转情况下可能超过当前硬限制，并导致房主连接断开。**

按方案允许六人同时说话，假设每人每 20 ms 产生一个音频帧、每个帧单独打成 SEND：

- 五名成员各自上行给房主，每人 50 包/秒，房主合计接收 250 包/秒。
- 房主将每名成员的语音转给另外四名成员：5 × 4 × 50 = 1,000 包/秒。
- 房主自己的语音再发给五人：5 × 50 = 250 包/秒。
- 房主总发送为 1,250 包/秒，尚未包括弹幕、状态及其他管理请求。

`server/src/hub.rs` 212–217 对每用户每秒处理的命令上限为 1,000。超限返回错误；`server/src/net.rs` 的 TCP/WS 循环遇到 process 错误会退出，因此后果不只是语音少一帧。只有部分直连时，应按实际剩余中转包率计算，不能依赖直连一定成功。

此外，TCP 和 WS 连接输出队列目前均为 32 项（net.rs 144、254），`Peer.send` 入队失败会通知关闭连接（hub.rs 37–40）。按未合包的 250 包/秒，32 项仅相当于约 128 ms 的到达量；这只是队列容量换算，不是网络一定在 128 ms 后断开的实测结论，内核缓冲与实际读写调度也会影响结果。单连接读写循环还优先处理输入，持续输入时的输出延迟需纳入定向验证。

建议在语音实现前补充发送预算：在客户端按目标将很短时间窗内的多个压缩音频帧或多个说话者帧合为一包，不做解码重编码；保留各子帧说话者、序号和时间戳，限制包长与等待期限，不能等待某个慢说话者拖住所有人。以每目标每 20 ms 至多一包作估算，房主对五个目标约为 250 包/秒，但实际能否这样合包、UDP 是否保持 1,200 字节内，以及新增缓冲延迟，必须结合所选编码和码率验证。

控制消息保留配额，语音过期在进入传输队列前丢弃。先做六人全中转和慢接收端的有限验证，再判断是否调整通用服务端资源预算/调度；不通过无限扩大队列或给 Rust 添加语音解析分支解决。20 ms 是本评估的容量假设，不是已确认的编码参数。

## 新功能的可行性与依赖

| 功能 | 评估 | 开工前或早期应解决的依赖 |
| --- | --- | --- |
| 选择控件 | 改动集中，风险相对小 | 保留 0.7.2 Activity 上下文修复、键盘/返回键与读屏行为 |
| 移除常驻通知 | 可行，属于连接生命周期改造 | 同步改启动/绑定服务、startForeground、权限、WakeLock、进程回收及前台恢复，不是删除通知 UI |
| 房间密码与锁 | 可行，服务端变化可以保持小 | 与 R1 共同明确“当前有效获准成员”和密码修改后恢复语义；目录锁仅为提示，不能代替房主校验 |
| 六人同步观影和实时弹幕 | 控制消息量较小，现有框架可复用 | 完整生命周期、播放器选型、各端访问 Emby、独立播放会话、时间线校准和过期状态处理 |
| Emby 免登录直接取流 | 有条件可行，是首要外部依赖 | 目标服务器的实际授权、六路并发、远程可达性、转码能力；第三方服务不能承诺普遍兼容 |
| 六人同时语音 | 可行但工程量大于文本弹幕 | 共同编码格式、网页/原生采集播放、混音与回声处理、上述包率预算、UDP 失败时的延迟控制 |
| Windows 客户端 | 复用 UI 的方向合理，但不是只打一个 exe | Rust 客户端握手及密钥方向、UDP、异步桥接、音频、WebView2 运行时、打包与下载元数据 |

Android 当前 MainActivity 仍启动前台服务并绑定，GameService 在连接与房间变化时刷新前台通知。Android 前台服务本身需要可见通知，因此移除常驻通知应改变相应生命周期，而不是继续运行“无通知前台服务”。旋转导致的 Activity 重建也应与真正进入后台区分。[Android 前台服务说明](https://developer.android.com/develop/background-work/services/fgs)

Emby 的用户 token 可用于后续 API，注销会撤销该 token；这不足以证明已有仅限当前电影、六位成员各自可撤销的授权能力。建议最早拿一台可管理 Emby 验证“房主登录、两台不同设备免输入账号各自取流、再扩展六路”，明确共享权限范围后再支持第三方服务器。没有合适分享能力的第三方服务器可以明确不支持，不能为了保证所有源可用而偷偷变成房主视频中转。[Emby 用户认证](https://dev.emby.media/doc/restapi/User-Authentication.html)

Windows 建议在公共传输接口稳定后，用现有翻棋/矿工先跑通客户端骨架，再加入观影和语音。当前 JS 依赖同步 NativeRoom 返回值，Tauri 的 invoke 返回 Promise，需要一层明确处理异步结果与失败的适配。保持一个业务实现，不能把 Promise 当成发送成功。[Tauri 调用 Rust](https://v2.tauri.app/develop/calling-rust/)

## 优化待办的收益排序

| 项目 | 评估与顺序 |
| --- | --- |
| O1、O3、O4 | 第一批值得做：相同正文只序列化一次、减少每次快照写 localStorage、复用同一次存档构建；源码证据直接，不需要先改协议 |
| O2 | 在 R3 的确认和补同步可靠后处理。两份 state 发给两个不同成员本属必要分发；真正可减少的是操作者同时收到 state 与含完整状态的 reply，不能误删其他人的广播 |
| O5 | 与移除通知和后台恢复一起处理高频时钟、UDP 稳定期保活及失败退避；避免拆成两次生命周期改造 |
| O6 | 先测掉帧与 GC，再改插值临时对象；目前不能承诺对真实设备帧率有明显收益 |
| Android 数组复制 | 中等优先级，先明确缓冲区所有权。语音则应在设计时避免逐包绕 JS/Base64，不必等全项目做零拷贝优化 |
| O7、O8、O9、O11 | 局部简化候选，相关文件已有改动时顺手处理；收益低于重复状态和存储，避免单独扩成大重构 |
| O10 | 保留待办，随桌面下载和发布资源入口一起评估；已有明确 HTTP 地址时可复用，不能从 TCP 端口猜 HTTP 配置 |

保留 v3 的 17 字节外壳。删掉几个长度字节并不能解决本轮主要问题，却会扩大跨端兼容成本。Rust 已共享 Bytes 正文，当前也没有证据要求引入全局缓冲池、unsafe 或新协议层。

## 建议实施顺序

1. 先修 R2/R3，定义并落实 R1 的成员恢复契约；随后修 R4/R5 的有界路径问题。每项只做相应定向验证。
2. 做通用房间拆分、密码与锁、前后台生命周期；同时把 O1/O3/O4/O5 的直接重复和无效唤醒收敛。
3. 尽早验证 Emby 免登录直取及跨端音频最小链路，再完成六人观影和实时弹幕。技术验证前置，不代表提前跑全量回归。
4. 在接口稳定后推进 Windows 基础客户端；语音完成包率、合包、抖动缓冲和回声控制后再接入多人。
5. 功能齐备后集中做六人、全中转、弱网、权限与跨端验收；其他微优化按测量决定。

未给出固定工期：Emby 是否提供合适授权及跨端音频链路尚未验证，会明显改变工作量。本轮只有 Git 同步、源码核对、官方文档核对、容量计算及文档检查；没有构建、运行回归、真实 Emby 取流、六人语音/网络压测、Windows 打包、提交推送或部署。
